# Join exchange — one valve joins our coordinator

Frame-by-frame spec for milestone **M-1** (steps 1-7) and **M2** (steps 1-12).
Source: freedo `docs/PROTOCOL.md` ("Pairing", "Router advertisement", "Session
id", "Link layer, planes and report timing", "Frame counter", "Enhanced ACK FCS")
and its `tado/` builders, at submodule commit `1812990`
(`reference/freedo`). freedo derives these from captures of the commercial
bridge; where freedo marks a fact as unverified on air, so does this file.

File references below are relative to `reference/freedo/`.

## Who does what

- **CC1312 (on-chip, timed):** the beacon answer (step 3), wake-up trains
  (steps 5, 6, 9), the Enhanced ACK (step 7 on), seq + frame-counter
  allocation and CCM* sealing of every outgoing frame, the pair-window key
  fallback (accept frames that fail the network key but verify under the
  pairing key, and tag that sender as "pairing key").
- **Host (not timed; the Java bench tool for M-1, the ESP32 gateway from M2):**
  network-key generation, the RA payload, the `d/pair`, `auth/token` and `time`
  CoAP payloads, the device DB. The host sends plaintext + destination + key
  selector down; the CC1312 seals and schedules. `time` must arrive within 5 s
  (step 10), well within a UART round trip.

## Sequence

### 1. Button long-press (user)
Runs `pair_factory_reset` on the valve: wipes its config records, erases the
network key, resets, and enters commissioning with the pairing key installed.
The valve's own commissioning window lasts **~2 minutes**
(`tado/pair_window.go` `MaxPairWindow` comment). There is no remote way to do
this. Open our own pair window just before the press.

### 2. Valve -> broadcast: Enhanced Beacon Request (pairing key)
27 bytes, repeated every **8.000 s**:

```
FCF 0be8 | seq | dstPAN ffff | dst ffff | srcEUI(8) | secCtrl 04 |
  sealed: counter(4 LE) cmd 07 FCS(2) | MIC(4)
```

The command id `07` is inside the ciphertext, so the frame must be verified
under the pairing key before it can be recognised (`tado/beacon.go`
`ParseBeaconRequest`).

### 3. Coordinator -> valve: Enhanced Beacon (pairing key) — **CC1312, timed**
32 bytes, unicast, **no wake-up train**, starting **2.4-7.4 ms** after the
request ends:

```
FCF 18ec (Frame Pending) | seq | dstPAN abcd (LE) | dstEUI(8) | srcEUI[0:3] |
  sealed: srcEUI[3:8] secCtrl 04 counter(4 LE) FCS(2) | MIC(4)
```

No IE, no payload; seq and counter are the next ones of the coordinator. A
request that arrives with a bad CRC gets no answer. freedo notes this has to be
generated on the radio side: a USB round trip to the host alone costs ~5 ms.

### 4. Valve -> broadcast: Router Solicitation (pairing key)
ICMPv6 RS in a broadcast Data frame, 1.5-2.8 s after the beacon.

### 5. Coordinator -> broadcast: Router Advertisement, **sent twice**
Within ~1.4 s of the RS, and not within 3 s of the previous RA (RFC 4861
`MIN_DELAY_BETWEEN_RAS`). During a pair window every RA goes out twice, each
behind its own full 254-frame train to `ffff`:

1. under the **network key**, FCF `59e8` (broadcast + Frame Pending);
2. ~6 ms after the first ends, under the **pairing key**, FCF `49e8`.

The two copies have consecutive seq and counter and the same payload. The RA
carries option 25 (IPv4 netmask `255.255.255.255`, gateway, DNS as
IPv4-mapped IPv6); freedo sends `0.0.0.0` when unset, not verified on a device.
Broadcast layout: FCF(2) seq(1) dst `ffff`(2) srcEUI(8) secCtrl(1) counter(2 LE)
ciphertext MIC(4); nonce `frame[0:13]`, aad `frame[0:16]` (`BuildBroadcast`).

### 6. Coordinator -> valve: `d/pair` (pairing key)
A unicast Data frame secured under the **pairing key**, carrying a CoAP **CON
POST** (`0.02`), UDP 5683 -> 5683:

- path `d/pair` (bare: no Uri-Port, no query), **empty token**;
- Content-Format **42**;
- option **2048** with **8 fresh random bytes** (single use, not stored);
- payload: one TLV, 1-byte tag + 1-byte length: `12 10 <16-byte network key>`.

Builder: `tado/build_resources.go` `BuildPairCoAP`. The valve sleeps (CSL), so
`d/pair` goes behind a wake-up train: the commercial bridge uses a 21-frame
train on the anchor of the joiner's latest Enhanced ACK. **For M-1, always use
the full 254-frame train** — it needs no anchor, so it works without M0. Send
`d/pair` ahead of anything else queued for the device.

### 7. Valve -> coordinator: `2.04` (network key)  — **M-1 gate**
The valve answers `2.04 Changed` **under the new network key within 30 ms**.
It is a unicast Data frame with ack-request: answer with an Enhanced ACK
starting 0-1 ms after it ends. If we miss the ACK (before M0), the valve
resends the same MAC seq with the next counter after 1.5-3.6 s; the join still
stands.

**M-1 passes** when a `2.04` from this valve verifies under our network key.

A `d/pair` to a valve that already talks the network key goes under the network
key and gets `2.03` instead — a useful negative check.

### 8. Valve -> coordinator: `auth/token` (network key)
The valve keeps its persistent token and resumes with `auth/token` (or
`auth/key` if its permanent token was never provisioned — not seen on air).
Answer `2.05` with **no options** and this body (`BuildAuthTokenBody`):

- TLV `025e`: session id, 4-8 bytes (we choose; freedo derives it from the EUI
  so it is stable across restarts);
- TLV `025f`: session lifetime in minutes, u16 big-endian, `05a0` = 1440 (24 h).

Never send TLV `0261` (the permanent token): the valve decrypts it with a
per-device key we do not have and would store garbage. Without a session id
the valve sends no option 2048 on later uplinks.

The answer goes through the downlink queue behind a full train (no anchor yet)
and is retried until its Enhanced ACK; a retransmitted request with the same
MID gets the same answer, not a new session.

### 9. Valve -> RS (network key), coordinator -> RA
As in step 5, now under the network key.

### 10. Valve -> GET `time`
Answer with a piggybacked **ACK `2.05`**, echoing MID and token, **no options**
(not even Content-Format). Body is protobuf, not TLV: `0d` + Unix epoch seconds
as u32 little-endian (`BuildTimeCoAP`, `EncodeTimePayload`). The valve
**discards an answer more than 5 s after its request**, so never queue it for a
later rendezvous.

### 11. Valve -> GET `d/<serial>/config`
Answer with the device config document (ETag + Block2). Out of scope for M-1;
see `PROTOCOL.md` "d/config write" and "Zone config document" for M2.

### 12. Valve starts reporting
Temperature and state reports on the home plane (`h/<home>/...`). **M2
passes** when a report verifies and decodes.

## After the join (keepalive)

The coordinator must keep broadcasting Router Advertisements every 200-600 s:
a device that hears none for about 20 minutes stops reporting and floods
Router Solicitations (`PROTOCOL.md` "Router advertisement"). This is why RAs
are part of the CC1312 autonomy layer (`PLAN.md` 3.2).

## Open points

- The valve sometimes sends a second Beacon Request after an answer; the reason
  is not known. Answer every verified request.
- Some solicitations go unanswered by the commercial bridge for no visible
  reason; freedo answers them all, and so should we.
- The RA option-25 contents are not verified on a device.
- Wall thermostat: same resources and `d/pair`, but pairing is **not verified
  on air** anywhere. Repeat M-1 for it before relying on it.
